\textbf{Setup.}
We use \modelname{} in BF16 on two \platform{} NPUs (64\,GB each) with
tensor parallelism $2$, CANN 8.3.rc1, PyTorch/torch-npu 2.7.1, and vLLM-Ascend
v0.11.0rc1. The direct baseline, \baseline{}, and PD-TDM use the same model,
TP group, precision, and arrival traces. Native CP sets outer
\texttt{max\_num\_batched\_tokens} to $B=2{,}048$, effectively bounding its
Prefill work to 2,048 tokens; PD-TDM uses $B=8{,}192$ with its separate
$C=2{,}048$ Prefill cap. The additional $B=8{,}192$ CP curve is the equal-$B$
reference, but CP has no separate $C$ knob and is not an equal-$C$ control.
Thus the direct comparison is between
complete deployment configurations, not a scheduler-only or equal-budget
ablation. T6 replays Azure-derived
conversation and code prompt/output pairs under a ten-second burst cycle. The
mean prompt/output lengths are 1,155/211 and 2,048/28 tokens, respectively.
Each point runs for 90\,s with a 30\,s warm-up; we report the median of three
arrival seeds. Strict TTFT/TPOT thresholds are 200/120\,ms for conversation
and 500/200\,ms for code. The reported PD-TDM path uses
\texttt{controller\_kind=slo\_pid}, an initial target of 0.30, a target range
of [0.05, 0.80], two-to-eight-iteration slices, and a 5\% free-KV watermark.
The controller updates every eight iterations, uses a four-credit token bucket,
a 5\% target violation rate, and a 2,048-token Prefill bound. It includes the
final admission and waiting fix. Each plotted attainment value uses all arrivals
in the steady-state window as its denominator, counting missing telemetry as
non-attainment; this is arrival-cohort goodput, with qualifying outputs counted
after the cohort end if needed, and uses the same 60-second
window. PD-TDM is evaluated as the complete
two-timescale path in Section~\ref{sec:design}; no result is attributed to the
slow controller alone.

\textbf{Azure bursts.}
Figure~\ref{fig:t6-main} reports the load sweep. At conversation scale
$k=3.0$, PD-TDM raises arrival-cohort joint-SLO attainment from 35.4\% to
69.1\% (+33.7 percentage points) and goodput from 1,318 to 2,500 output
tokens/s. At code scale $k=4.9$, attainment rises from 5.7\% to 79.5\%
(+73.8 points) and goodput from 56 to 282 output tokens/s. These are
representative strict
operating points, not universal speedup factors: the code baseline starts
near zero attainment, and wider SLOs move both systems toward a ceiling. The
observed effect is therefore best interpreted as shifting the latency
distribution relative to a joint threshold, rather than proving an unconditional
raw-throughput advantage.

The result is consistent with the intended mechanism: explicit $P$ opportunities
advance queued prompts without inserting their work into every Decode iteration.
Telemetry shows $r$ moving from 0.30 to 0.80 and pure $P$/pure $D$ iterations
with Decode inter-arrival P50/P99 of 189/203\,ms. This confirms phase selection,
not a fixed mixed-batch kernel tax; the iterations have unequal work.

\textbf{MaaS replay.}
We replay a 76-minute MaaS arrival trace. Compression places arrivals in
$[0,4560)$\,s, so paper-facing goodput uses the active $[30,4560)$\,s interval
instead of the driver's idle tail. The cohort has 35,345 arrivals; 21 CP and 3
PD-TDM one-token records have undefined TPOT telemetry and are conservatively
counted as non-attainments. Table~\ref{tab:maas} reports matched-record
latencies but full-cohort attainment. PD-TDM lowers mean/P99 TTFT by
15.1\%/10.4\%. Both systems are near the original $3\times$ SLO ceiling;
$1.2\times$ reclassification separates them, but is post-hoc. This fixed-ratio,
single-seed replay supports the TTFT direction, not adaptive control or
cross-workload generality.

\textbf{Operating boundary and limitations.}
Synthetic boundary runs show the expected tradeoff: Prefill-sensitive cells
can benefit from more $P$ opportunities, whereas long-output Decode-heavy cells
can favor mixed prefill. These single-seed runs, some with client timeouts, are
directional counterexamples rather than capacity estimates. Evidence is limited
to \modelname{}, one two-NPU platform, one pinned stack, and the stated budgets;
it does not establish equal-$B$ superiority, a kernel-level cause, or an optimal
$r$. Runtime changes can alter the result. A fixed-versus-reactive ablation
under workload/SLO changes remains future work.
